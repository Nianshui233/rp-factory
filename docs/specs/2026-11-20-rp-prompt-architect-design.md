## 1 意图与为什么

把本目录下 4 份面向酒馆的多轮对话提示词，重组成一个**可被编码 agent 直接加载的能力包**，用它把用户的一句话概念，编译成一套彼此不打架的 RP 设定产物（世界观 / 角色卡 / 场景卡 / 数值系统）。

**为什么不是照搬。** 原始 4 份是写给"酒馆里那个模型"的，各自独立、各自完整，靠用户自己维持一致性。但它们在原文里已经互相声称依赖：

- `RP场景生成器.md:3` —「若用户提供世界观或其摘要：你必须遵守其中的硬规则，不得写出与之冲突的内容」
- `AI-RP 角色架构师.md:24` — 阶段 0 评估维度第一项：「世界观/题材：能确定语言风格、禁忌、冲突类型」
- `AI-RP 系统架构师.md:218-220` — 一致性铁律：`axes.name`、`range`、`initial`、阈值标签必须在**系统卡 / 变量结构 / 更新规则 / 状态栏四处用同一套名字与数值**，否则出现「系统卡叫 corruption、变量叫 堕落值、状态栏叫 沉沦度」的漂移
- `RP 世界观设计助手.md:56` 原则 5 — 关键设定不替用户拍板

这些依赖在原文里是**声明**，不是**机制**。本设计的核心就是把它变成机制。

## 2 目标 / 非目标 / 反目标

**目标**

1. 一条概念 → 一套产物，跨产物的命名、硬设定、内容边界自动一致。
2. 双模态：既能产出可粘贴进酒馆的提示词条目文本，也能直接落成工程文件。
3. 可从任意阶段进入（"我只要一张场景卡"合法）。
4. 原型阶段就能用真实旧项目跑通验证。

**非目标**

- 不改写原文的内容判断（什么算好的世界观、什么算好的角色卡，一律沿用原文标准）。
- 不做酒馆插件，不生成 HTML 前端、正则、状态栏。
- 不接 TavernWeave 的插件清单、测试、分发。

**反目标（技术上都成立，但算失败）**

- 产物齐全但命名漂移（世界观叫「蚀月教团」，角色卡里写「月蚀教」）。
- 主 skill 变成一个巨大的提示词，把 4 份内容塞进一个 SKILL.md，失去按需加载。
- 双模态变成两套模板并行维护，改一处忘一处。
- 追问退化成问卷轰炸，用户第 3 轮就退出。

### 3.1 保真策略（解 200 行预算与"不改写原文"的冲突）

规则**不可丢**，只允许两种压缩：

1. **合并同类**：原文并列的多条 bullet 若判定同一件事，合并为一条，保留各自的原文编号。
2. **例子外移**：示例、反例、正例统一挪进对应的 `templates/*.yaml` 注释或 `examples/`，阶段文件只留规则句。

每个 `stage-*.md` 在**构建期**必须对照一份覆盖清单（`docs/coverage-checklist.md`，构建期产物，不随包发布）逐条打勾，列明它承载了原文哪些编号条目。任意规则缺失，对照清单就能立刻发现。

**不允许**：改变规则的强度（"必须"改"建议"）、删掉例外分支、删掉否定式约束。

### 3.2 自包含原则

本 skill 建好之后，`参考/原始提示词/` 下那 4 份源文件**会被删除**。因此：

1. `SKILL.md`、`references/**`、`templates/**` 中**不得出现任何指向源文件的路径**（包括 `../../RP场景生成器.md` 这类相对路径）。
2. 不得写 `覆盖原文：RP 世界观设计助手.md 原则 3` 这类**文件名回溯登记**——源文件消失后它只是无从核对的噪声。规则编号可以保留（如"原则 3"），文件名不保留。
3. 运行时不依赖源文件存在；迁移是一次性的，搬完就断奶。
4. 构建期产物（`docs/specs/*.md`、`docs/coverage-checklist.md`）不进 skill 的加载路径，可以放心引用源文件。

**代价与应对**：源文件删了就再也无法回到原文核对。所以删除应当放在验证（§11）通过之后，且验证基线 `examples/` 必须先把"什么是好产物"固定下来。

## 4 选型

### 4.1 已否决

**A · 并列产物库**：主 skill 按关键词选一个子 skill 干活。
否决理由：每份各自为政，原文声称的跨产物依赖无人执行——而这恰好是最值钱的部分。命名漂移会在第 3 个产物出现时爆发，返工成本高于一次做对。

**B · 全局单一提示词**：把 4 份合并成一个大 SKILL.md。
否决理由：角色卡字段规范和世界观 18 条原则加起来近 500 行，合并后无法按需加载，每次调用都吃满上下文。

**D · 独立多 skill 目录**（`skills/rp-world-bible/`、`skills/rp-rolecard/` … 各自可被发现）
否决理由：跨目录读同级 skill 需要相对路径 `../rp-rolecard/SKILL.md`，在 Pi / Claude Code / Codex 之间路径基准不一致，原型阶段不值得背这个脆弱性。**注意：这是可逆选择**——若验证后确实需要"用户直接喊『只做角色卡』就命中子 skill"，把 `references/stage-*.md` 搬到独立目录是纯文件搬移，内容不用重写。

### 4.2 采纳：C · 流水线 + 契约

```
世界观 ──► 角色卡 ──► 场景卡
   └──────────┴──► 数值系统
```

主 skill 只做三件事：**判阶段**、**读写契约**、**派发纪律**。它自己不生成任何设定内容。

- 每个阶段进场先读契约、出场写回契约。
- 可从任意阶段进入，缺失的契约项先补采访问一次，问不到才打 `[待定]`（§7）。
- 数值系统可以从世界观直接进入（不需要角色卡在它前面）。

**为什么 C 让双模态免费**：契约是共享事实源（索引 + 命名权威，见 §6）。文本模态 = 把产物渲染成可粘贴条目代码块；工程模态 = 把产物写成文件。两种模态共用同一份草稿，不维护两套模板。

## 6 契约 contract.yaml

```yaml
project:
  name: ""                 # 世界/作品名，可暂定
  mode: "text | engineering"
  rp_form: ""              # 1v1 / 多人 / 跑团风格 / 旁白主导
  language: "zh"

stages:                    # 每阶段状态，不用标量 stage_reached
  1: none | partial | done | skipped
  2: ...
  3: ...
  4: ...

content_boundaries:        # 必须最早锁，所有阶段共享
  rating: ""               # 全年龄 / R18 / 自定义
  hard_no: []              # 明确不出现的元素
  soft_no: []

naming:                    # 铁律锚点：跨产物唯一事实源
  world: ""
  factions: []             # {id, name, alias[]}
  places: []               # {id, name, scope}
  systems: []              # 超自然/科技系统
  axes: []                 # {name, range, initial, provisional?, levels[{label}]}

hard_settings:             # 已锁定、不可改
  - id: ""
    text: ""
    source: "用户确认 | 推导"
    locked_at_stage: 1

pending: []                # [待定] / [推断…待确认]
decisions: []              # {stage, question, answer, why}
artifacts: []              # {type, path | inline_ref, version}
```

**契约是索引与命名权威，不是产物全量中间态。** 世界观正文、角色卡 `psychology`/`behavior`/`speech`、数值系统的 `calculation`/`thresholds`/`boundaries` 都**不**进契约——它们存在 `artifacts[]` 指向的产物里。契约只回答两件事：这份东西存不存在（`artifacts` + `stages`）、同一个东西在各产物里叫什么（`naming`）。

理由：把 767 行的世界设定复制进契约，就是 §2 反目标里的"两套模板并行维护"换个名字。

**零漂移检查必须同时读契约与产物**：`naming.axes` 是投影，投影可能与 `axis-system.yaml` 正文不一致。所以命名门是一个**渲染时交叉核对**步骤（`pipeline.md` 的最后一道门），不是"查契约就够了"。

**读写规则**

- 阶段文件只允许写自己负责的键区。
- 写已存在的键 = 冲突，必须停下问用户，不许静默覆盖。
- `naming.axes` 由 stage-4 独占接管；stage-2/3 可写 `provisional: true` 的临时项。

| 键区 | 独占写者 |
|---|---|
| `project.*`、`content_boundaries.*` | 主 skill（阶段 0 判定 + 首轮提问） |
| `naming.world` / `factions` / `places` / `systems` | stage-1 |
| `naming`（角色相关新增）| stage-2 |
| `naming.axes` | stage-4 接管；stage-2/3 可写 provisional |
| `hard_settings` | 各阶段追加，只有用户确认才 `locked` |

## 7 追问协议

每题结构固定（用户指定）：

```
【问题 N】<一句话问题，具体到当前项目，不空问>
- A：<具体后果的描述>
- B：<具体后果的描述>
- C：<具体后果的描述>
- 我的建议：A
  为什么：<基于已锁定的哪条设定 / 哪条原文原则>
  影响：选 A 则 <下游什么会变>；选 B 则 <下游什么会变>
```

**stage-0 不单独提问。** 主 skill 只判"够不够开工"；`content_boundaries` 与 `rp_form` 的题目**并入下游首轮**，避免"先 7 问再 7 问"的问卷轰炸。若用户一开口就点名要某个产物（"我只要一张场景卡"），边界题并入该产物阶段的首轮。

**预算由阶段自行声明**：

| 阶段 | 首轮上限 | 后续每轮上限 | 轮数上限 |
|---|---|---|---|
| stage-0 开工判定 | 0 问（并入下游首轮）| — | — |
| stage-1 世界观 | 5–7 问（其中 ≤2 个是内容边界/形式题）| 8 问 | 无限轮，但收敛信号达成即提议出终稿 |
| stage-2 角色卡 | 3 问 | 3 问 | 2 轮 |
| stage-3 场景卡 | 10 问 | 8 问 | 无限（原文未设） |
| stage-4 数值系统 | 4 问 | 4 问 | 2 轮 |

**上游缺失时：先问一次，再打待定。** §4.2 的"缺失项打 `[待定]`"是**兜底**，不是第一反应。任何阶段发现上游契约项缺失且会破坏本阶段的可判定性（如场景卡缺 `naming.world`/`factions`），允许发起一次**补采访问**：上限 3 问、计入本轮预算、只问会影响可判定性的项。问不到才写 `[待定]`。

**乱序进入与轴名。** `stages` 是每阶段状态而非标量，乱序合法。stage-2/3 若需要轴名（好感度、堕落值等），可写入 `naming.axes` 并标 `provisional: true`；stage-4 接管时逐条确认或改名，改名必须**回写所有已引用它的产物**，并记入 `decisions`。

**降级链**（沿用 `AI-RP 角色架构师.md:66-80`）：追问无果 → 构造 A/B 两组对比设定供二选一 → 用户说"你来定"则自主补全并标 `【AI补全·可替换】` → 仍无回应则通用假设 + 标注 + 说明。

## 8 双模态

| | 文本模态 | 工程模态 |
|---|---|---|
| 交付 | 可粘贴进酒馆世界书的代码块 | 项目目录里的文件 |
| 实现 | 契约 + 草稿 → 按原模板渲染成一个 ```yaml 代码块 | 契约 + 草稿 → 写盘 |
| 附加 | 保留 `【未知】`/`【AI补全·可替换】`，末尾附补全清单 | 同上，另附 `contract.yaml` |
| 切换 | 用户说"给我能粘贴的""存成文件"随时切换；切换不重跑阶段 | 同左 |

默认 `mode: text`（贴合原文产物形态）；工程模态在用户提出或项目已有目录时启用。

### 8.1 产物一律 YAML

四类产物的模板与输出**全部是 YAML**，没有例外：

| 产物 type | 文件 | 键风格 |
|---|---|---|
| `world-bible` | `world-bible.yaml` | 中文顶层键，根键 `<世界名称>` |
| `rolecard` | `rolecard.yaml` | 英文顶层键，根键 `character` |
| `axis-system` | `axis-system.yaml` | 英文顶层键，根键 `meta` / `axes` / … |
| `scene-sheet` | `scene-sheet.yaml` | 中文顶层键，根键 `<场景名称>`（转写，见下）|

**场景卡是唯一需要转写的**：原模板是 Markdown 的 `- **字段**：` 列表。转写规则：

1. 原 10 节 → 10 个二级键：`概览` / `空间结构` / `关键区域` / `出入口与安防` / `生态` / `资源与可破坏物` / `线索` / `时间与事件` / `规则` / `边界`。
2. 原 `- **字段**：` → `字段: ""`；原缩进子弹 → 该键下的列表或对象。
3. 原文里的括号提示（`（例：…）`）→ 移入该键后的 `#` 注释，结构位留空字符串。
4. 不得因为转 YAML 而丢掉任何一个原字段。

文本模态输出统一是一个 ```yaml 代码块；不用 Markdown 表格、不用 `- **字段**：` 这种列表形式。

工程模态只写盘四类产物 + 契约，**全部为 `.yaml`**；不做 ST 可导入的 JSON——那是 TavernWeave 的事。

## 18. 世界书调优（2026-11-20 追加）

阶段 7 生成世界书时原本只有"切哪几块"（§17），没有"参数怎么定"。补一份 `references/worldbook-tuning.md` 并把参数写回切法表。

**资料前提**：两个飞书 wiki（`ZJ9Yw0X7JipJrlkAoT0cku54nMb`、`QKkYwUsGAivp4ukhvBRcYlf6nCd`）需要登录态，抓取工具没有 cookie，重试与检索均失败——不复用这两篇的结论。改以官方 World Info 文档 + 本机 `public/scripts/world-info.js` 实现为准，参考包 `我，非我 世界书.json`（22 条）做经验校验。

**收进 skill 的硬事实**（都与"社区习惯"有出入）：

1. 三个灯里不用 🔗 向量化。理由不是先进与否，而是**错触发方向错**：语义相近却指错人，AI 会照 A 的设定演 B，且难发现；绿的关键词漏了是召回不足，加词就补回来了。
2. `matchWholeWords` 必须显式 `false`。官方文档写默认开启、本机默认 `false`；中文字符属 `\W`，整词匹配对中文只减命中不加精度。
3. 绿灯条目一律 `excludeRecursion: true`。常驻条目正文会点名势力与地点，递归一开就顺次点亮它们，等于把关键词条目变成半个常驻。参考实现 22 条全书如此。
4. `order` 三档：骨架 92–100 / 实体 78–90 / 状态栏协议 70。全填 100 等于没有顺序。
5. `position` 五个位置换成风险说明：`2/3` 作者注关闭时整条被忽略、`5/6` 会被解析成示例对话、`7` outlet 未填名直接跳过。
6. 关键词 8–15 个、纯文本 key 不支持逗号（要匹配带标点只能写 `/.../flags` 正则）、标题与关键词都不进上下文。
7. 预算：常驻 5000 字（校验器 W09）+ 单条 ≤1000 字 + 全局 Context 25% 默认，插入优先级"常驻 → 关键词命中 → 递归带出"。

### 18.1 教程补充（用户提供《世界书》全文后）

用户把飞书那篇《世界书》（作者 @破坏轨道）下载成了本地 md，此前抓不到的两页之一因此拿到全文。它讲的是 2023 年的旧版酒馆，与当前实现的差异已逐条核实，补进 tuning：

1. **插入位置是效力阶梯**：角色定义之前（最弱）→ 之后（稍强）→ 作者注之前（较强）→ 作者注之后（极强）→ `@D`（可变）。原来只写了"要压过角色卡时用 `1`"，漏了 `3` 是全套最强档、且要配合作者注的插入深度。
2. **常数 + `@D` = 第二个作者注**。状态栏协议就是这么生效的，原文档没点明这层机制。
3. **先比位置，再比 `order`**。原 tuning 只说"`order` 越大越靠下"，没说跨位置时位置优先；补了那张 7 条的排列示意。
4. **首尾各约 0.9%（≈900 token）是强记忆区**——"position 0 最弱"只在长对话成立，短上下文里顶端也几乎不会被忽略。
5. **扫描深度单位是消息条数**，不是教程说的"一对"。本机 `chatForWI` 是 `coreChat.map(...).reverse()` 后按条数切片，所以深度 2 覆盖"你最新一句 + 角色上一句"，够用。
6. **概率不可靠**：教程明说"大概率触发小概率事件"，本包据此加了警告——要严格随机别用 `probability`。
7. **均匀排序别用**（策略优先级本就低于 `order`/`position`）。
8. **中文书名乱码问题在本机已修**：`src/middleware/multerMonkeyPatch.js` 用 `Buffer.from(str,'latin1').toString('utf-8')` 把 `originalname` 转回来，所以 `extensions.world` 依赖的"文件名 = 书名"在中文下成立；老版本会变一串字符，story 里给了重命名补救。
9. **新增第十二节「分档设定」**：拿状态栏/轴的阶段词当关键词，实现"数值到某档才解锁"。这是教程"用正则触发世界书做好感度系统"的整理版，但明确写了两条代价：格式一改就失配、字符串包含不等于数值比较。

## 21. 前端界面静默失败：HTML 实体（2026-11-20 追加）

**现象**：建卡向导在酒馆里只剩一条 2px 高的黑边，控制台一句 `Invalid or unexpected token`，界面空白，但消息原文仍是 `<建卡向导>`（正则确实跑了）。

**根因**：正则替换出来的代码块要经过 `encode_tags → Showdown → 解析成 DOM → 再插回消息容器`，实体在中间被解码两次。模板里 `esc()` 写的是 `'&': '&amp;'`、`"'": '&#39;'`，进 iframe 时变成 `'&': '&'`、`"'": '''`——右边那个 `'''` 直接让整段 `<script>` 语法错误。脚本一死，酒馆助手量到的 body 高度就是 2px。

**修法**（两条）：

1. 正文与 CSS 里不写实体；需要 `&` 就写 `&`，空格用 `white-space`／`u00a0`。
2. JS 字符串里的实体用 `&` 拼（`'&amp;'` 等）——`&` 在求值时才变 `&`，源码里没有字面 `&`，管线没东西可吃。

**落地**：三个模板（`wizard-ui` / `statusbar` / `opening-ui`）与两个 dry-run 示例全部改掉；新增 `scripts/validate-frontend.py`（F01–F08：骨架、外链、`eval`、**内联脚本里的实体**、硬编码 vh、`innerHTML` 无 `esc()`、标签配平、外部样式）；`frontend-conventions.md` 新增「三之一 实体陷阱」并把前端门从 8 条加到 9 条；`stage-5` / `stage-6` / `pipeline` / `SKILL.md` 同步。`opening-ui.html` 顺手把 `getChatMessages` 包进 try/catch（不在正式聊天里预览时留白而不报错）。

**验证方式可复用**：用 `puppeteer-core` + 本机 Chrome 打开 `http://127.0.0.1:8000/`，点开角色卡，读 `.mes_text iframe` 的高度与 iframe 内的 DOM——高度 2px 就是脚本死了，高度正常才叫渲染成功。只跑 `node --check` 不够：`&` 这类写法在源码里合法，问题只出现在管线解码之后。

## 24. 变量系统：两条线，两种可靠性（2026-11-20 追加）

MVU 与 EJS 的边界、以及它们在 pipeline 里该站在哪，来自一次真机实验（14 人群像、两条轴、手搓方案、导入真实酒馆跑两轮）。实验记录不随包发布。

**三条取证结论**（六实例 + 一预设交叉验证）：
1. **结构写在 zod 脚本里，不写 `$meta`**：`苏玉` / `时雨不终` / `二十一人会` 全用 `registerMvuSchema`，`[initvar]` 里一个 `$meta` 都没有。
2. **状态栏绑 MVU**：`findRegex` 是 `<StatusPlaceHolderImpl/>`、`maxDepth: 2`，桥接靠 `waitGlobalInitialized('Mvu')` + `Mvu.events.VARIABLE_UPDATE_ENDED`。
3. **EJS = 控制器 + 被控条目**：控制器 `constant`，被控条目 `disable: true`，靠 `await getwi(null, '条目名')` 装载。

**实验打出来的六条硬事实**（都已进计划 Task 23/24/25）：
- `z.coerce.number()` 遇脏值产出 `NaN`，在 `.transform` 之前就拒整条更新 ⇒ 必须 `.catch(初值)`；
- native 世界书 `uid` 必须等于 `entries` 键，错位时面板**静默**丢条目（实测丢 9 条）；
- `<UpdateVariable>` 要两条正则（`promptOnly` 不发给模型 / `markdownOnly` 不显示），`<StatusPlaceHolderImpl/>` 默认藏；
- 卡内脚本默认**不跑且不报错**，要在酒馆助手里给该角色启用（`enabled.characters` 白名单）；`importFromJson` 不会把 `character_book` 落成世界书；
- 「变量初始化成功」弹窗**书里一条 initvar 都没有也照弹**，不能当证据；只有改一个与 `prefault` 不同的值再问一次才算验过；
- 卡内脚本跑在独立 iframe，`Mvu` 挂在 `window.parent`。

**四条 Ruling**：
- **常量预算不设上限**。字数只打印不判定——MVU 三件套把常驻从 4.7k 顶到 8.7k，那是"该写的都写了"的结果，砍它等于砍规则可读性。
- **`ejs` 默认不建**。只有"同一份内容放书里 N 份会 N 份全进上下文"才建控制器；只报档名的控制器多半冗余——实验里第 4 楼的行为能对上档位，很可能来自书里的阈值表而不是控制器。
- **数值上限遇 OOC 放行且静默**。`caps` 是给模型的建议，玩家显式命令改数值时照办。
- **`<StatusPlaceHolderImpl/>` 默认藏**，做了 `statusbar` 阶段再撤。

**两个阶段的分工**：`mvu` 只做投影（轴 → 可执行的 clamp/check），不重新设计数值；`ejs` 只做切换（把 `cast` / `scenes` 已产出的分档内容变成按变量生效），不新写内容。两者都在 `axes` 之后、`opening` 之前，`mvu` 必在 `ejs` 前。

## 25. §24 落地：从讨论到实现的三处漂移

§24 定的是"做什么"，实现时三处口径被现场证据改写，记在这里免得以后按 §24 的字面去用：

1. **`E01` 的第一块守卫不是"每条 `getvar` 前都要 `typeof`"**，而是"首个 `<%_ … _%>` 块里声明的变量，后面才可以直接用"。`时雨不终` 的控制器在循环里用 `getvar` 取字段，没有逐条守卫——按字面查会把正确的写法判红。
2. **`E06` 的"上界盖满 100"只在分支链没有 `else` 时成立**。末尾是 `else` 兜底时，数字上界停在 79 是对的。
3. **`E02` 只数第一个块的 `var`**。循环体里的局部变量不该算进"防重声明"的统计，否则 10 个变量 5 个守卫会被误判成"少了一半"。

另外两条实现细节写进了 `validate-contract.py`：

- `stages` 改成名字键之后，**旧契约里的数字键必须按"七阶段编号"解释**（`5` = `opening`），不能按新的九阶段顺序解释成 `mvu`。这个错位不会报任何错，只会静默算错——校验器给 WARN 提示改名，别只改数字。
- `stage_map()` 会被多个检查函数各调一次，`warn()/fail()` 因此要去重，否则同一个问题刷四遍。

**门数与体量**：十道门 → 十一道门（加 `变量门`）；`SKILL.md` 上限由 150 改为 300。九阶段 + 十一道门之后，150 行的压缩成本（把三条规则挤成一行）已经高于收益——合并出来的句子会在下一次修改时被误读。

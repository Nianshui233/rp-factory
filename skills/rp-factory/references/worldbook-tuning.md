# 世界书怎么调

阶段 7 出包时按这份文件定参数。规则来自 SillyTavern 官方 World Info 文档、本机 `public/scripts/world-info.js` 的实现、以及本机酒馆的行为实测。凡与"社区习惯"冲突，以实现为准。

**先写后配**：正文写什么见 `references/worldbook-writing.md`；条目怎么被选中、预算怎么算、大卡（>200 条）怎么做见 `references/worldbook-engine.md`；这一份只管参数。

## 一、三个灯

| 灯 | 字段 | 行为 |
|---|---|---|
| 🔵 蓝 | `constant: true` | 不看关键词，每轮都插 |
| 🟢 绿 | `constant: false` + `selective: true` | 主关键词命中才插；配 `keysecondary` 时再按 `selectiveLogic` 判一轮 |
| 🔗 链 | `vectorized: true` | 允许被 embedding 相似度激活（需装 Vector Storage） |

本包只用蓝与绿。链的问题不是"不先进"，是**错触发的方向**：语义相近却指错人，AI 照着 A 的设定演 B，很难发现。绿漏词只是召回不足，加词就补。

## 二、参数套餐

出包时按条目类型直接套，不要每条现想：

| 条目类型 | `constant` | `order` | `position` | `depth` | `excludeRecursion` | `preventRecursion` | `ignoreBudget` | 关键词 |
|---|---|---|---|---|---|---|---|---|
| 骨架 / 常驻规则 | `true` | 95–100 | `0` | `4` | `true` | `true` | `false` | `[]` |
| 实体细节（势力 / 地点 / 系统） | `false` | 70–90 | `0` | `4` | **`true`** | `false` | `false` | 8–15 个 |
| 状态栏协议 | `true` | 70 | `4` | `2` | `true` | `true` | **`true`** | `[]` |
| 隐藏信息（防剧透） | `true` | 85 | `4` | `2` | `true` | `true` | `false` | `[]` |

其余字段一律：`selective: true`、`selectiveLogic: 0`（AND_ANY）、`probability: 100`、`useProbability: true`、`matchWholeWords: false`、`caseSensitive: null`、`disable: false`、`group: ""`、`groupWeight: 100`。

- **常驻也要 `excludeRecursion: true`**：常驻正文点名一堆势力与地点，递归一开就成了"永久点亮器"。实测 `尸变纪元` 46 条里有 58 条这样的边，`我，非我` 21 条里 62 条。
- **`preventRecursion: true` 给常驻**：反过来锁死"这条不许拉别人"。常驻条目每轮都在，是唯一稳定会往递归缓冲里灌东西的来源。
- **`ignoreBudget: true` 只给状态栏协议**：它是每轮都要在的界面锚点，被预算挤掉就等于状态栏消失。别给别的条目——那是绕过预算限制的后门。
- `matchWholeWords: false` 显式写。官方文档说默认开，本机默认 `false`；中文无空格分词，开整词匹配只会更难命中。
- `depth` 只在 `position: 4` 时有意义，别的值填了也不读。

## 三、关键词

**每条绿灯条目 8–15 个**，宁宽勿漏。五个来源：本名/别名/译名（`守夜所`、`灯所`）、关系指代（`次席`、`老邵的上司`）、场景指代（`巡堤`、`点灯`）、同义口语（`熄灯`、`断火`）、跨场景关联（`盐票`、`灯芯配额`）。

规则：

- **纯文本关键词不支持逗号**——逗号是分隔符，想匹配带逗号的串只能用正则。
- 正则关键词写成 `/.../flags`，与普通关键词混排、并列生效：`/(?:守夜所|灯所)/i`。多词、可选词、中文标点都靠它。
- 别用标题词当关键词（`白潮的秘密`、`势力介绍`）——聊天里没人这么说。要按"这条内容会在什么对话里被需要"反推。
- 关键词只是索引：**条目标题与关键词都不进上下文**，所以正文必须自己站得住，别写"如上所述"。
- **不用单字关键词**（`月`、`枫`、`家`）：`include_names` 关着时它们在任何一句里都成立，3k 字的角色条目就这样被拉进来。同理不用泛词（`城`、`王国`、`我们`）。`W19` 查这一条。
- **关键词不要互为子串**：`灯` 与 `灯所` 同时存在时，短的那个会把长的条目也一起点亮。要留就只留长的，短的改用正则加边界。`W20` 查这一条。
- **`include_names` 关着时，名字不是可靠的触发器**：它只能靠正文里出现。要大范围命中就把名字放进 `keysecondary` 并配 `AND_ANY`，别指望"角色一说自己名字"就点亮。

## 四、插入位置：一条从弱到强的阶梯

上下文是个有限容器，越靠下的 prompt 对当前回复影响越强，越靠上越容易被后续内容淹没。五个位置就落在这条阶梯上：

| `position` | 名称 | 效力 | 什么时候用 |
|---|---|---|---|
| `0` | 角色定义之前 | 最弱 | 默认。世界观、势力、地点、常识 |
| `1` | 角色定义之后 | 稍强 | 要压过角色卡自带的设定时 |
| `2` | 作者注之前 | 较强 | 需要强力的规则；作者注关掉时整条失效 |
| `3` | 作者注之后 | **极强** | 想让 AI 必须遵守的规矩；配合调作者注的插入深度，是全套里最强的位置 |
| `4` | `@D` 按深度插入 | 可变 | 状态栏协议、当轮临时状态、防剧透信息 |
| `5` / `6` | 示例消息前 / 后 | — | ⚠️ 会被**解析成示例对话**，不要拿来放设定 |
| `7` | Outlet | — | 手动用 `{{outlet::名字}}` 定位；`outletName` 空 = 直接跳过 |

三条容易漏的：

- **常数 + `@D` = 第二个作者注**。`constant: true` + `position: 4` + 小 `depth`（0–2）的条目，每轮都插在聊天记录最下面，比 position 0 的常驻条目强得多。本包的状态栏协议就是这么放的。
- **`2` / `3` 骑在作者注上**：作者注的插入深度一改，它们的实际位置跟着动。作者注关掉（或深度异常）时这两档会整条失效——所以核心规则不要只放这里。
- **首尾各约 0.9%（≈900 token）是"强记忆区"**。刚开聊时 position 0 也几乎不会被忽略，聊长了才会滑出去——"position 0 最弱"只在长对话成立。

## 五、顺序与预算

### `order` 只在同一位置内排序

同位置同时触发时，`order` 越大越靠下、影响越强；位置不同则位置优先，`order` 再大也压不过下面的位置。不填则按条目创建时间排——**不排序 = 不可控**。

排布原则：**按重要性排，最想让 AI 记住的放最靠下**；背景设定放 position 0；状态栏与状态栏规则放靠下的位置——如果 AI 聊着聊着忘了输出状态栏，先把它那条往下移，而不是改提示词。

### 同轮命中的装填顺序

只有两条依据：**sticky 排最前，其余按 `order` 从大到小**。没有“常数优先于关键词”，也没有“直接命中优先于递归带出”——常驻先装只是因为我们给它高 `order`。想保谁，就给谁高 `order`。

### 预算

- 预算 = `Context % × 上下文窗口`（默认 25%）；`Budget Cap` 设了绝对值时取较小，`0` = 不生效。
- 装到预算就跳过后续条目：**命中了也不插**，递归随之停止。预算是硬墙。
- 常驻合计参考 ≤8000 字（`W09` 只报数；超了改成关键词条目，别压句子）。
- `Context %` 调到 100 时，**表面看条目都进去了，被挤掉的是聊天历史**，表现是“AI 忘了前文”。
- 溢出警报默认**关**，爆了界面什么都不说。交付说明里要写。

## 六、全局激活设置（交付时给用户这张表）

这些是**用户端**设置，世界书文件里改不了。推荐值是"能跑通就行"的默认派；右列写改大了会怎样，因为大卡作者往往会把它们拉到极端。

| 设置 | 推荐 | 改了会怎样 |
|---|---|---|
| Scan Depth | `2` | 单位是**消息条数**（从最新往前数），不是"轮"。覆盖"你最新一句 + 角色上一句"就够；到 6 以上等于反复塞旧设定，预算翻倍 |
| Context % | `25` | 100 = 预算等于整个上下文，条目全进去、聊天历史被挤掉 |
| Budget Cap | `0` | 设为绝对值会盖过百分比 |
| Recursive Scan | **关** | 开了就是全局放大：命中一条可能带出一串。开之前必须把 `excludeRecursion` 写满 |
| Max Recursion Steps | `0` | `0` = 不限层。递归开 + 不限层是最容易雪崩的组合 |
| Include Names | **开** | 名字进扫描缓冲，才能"某角色说话"点亮他的条目 |
| Match Whole Words | **关** | 中文必须关：开了整词边界几乎匹配不到中文词 |
| Case Sensitive | 关 | 中文无大小写 |
| Alert on Overflow | **开** | 关着时预算爆了没有任何提示（默认关） |
| Use Group Scoring | 关 | 只在用 `group` 互斥时需要 |
| Lore Insertion Strategy | Character Lore First | 卡绑的书优先。**均匀排序别用**；`order`/`position` 的优先级永远高于这个策略 |

**交付时问用户实际值**。同一个包在「25% + 递归关」与「100% + 递归开不限层」下是两种行为：前者靠关键词召回，后者靠排除字段保命。

## 七、递归：想用才用

条目正文提到别条关键词 → 那条会被一起插进来。这是唯一"不写关键词也能带出设定"的机制。

官方最小例子：条目 #1 关键词`贝西`、正文「贝西是一头奶牛，和鲁弗斯是朋友」；条目 #2 关键词`鲁弗斯`。开递归 → #1 被触发时带出 #2；关递归则不会。

- 想要它：给“事件”条写正文时**故意点出**关联实体（`伏击者为湖心教团` 会带出教团条目）。
- 不想要它：给每条设 `excludeRecursion: true`（本包默认），并且别开全局 Recursive Scan。
- `preventRecursion: true` 是反向锁：这条被激活后不许再触发别人。常驻条目一律加。
- `delayUntilRecursion` 让条目只在递归轮次命中，用来做“第二层真相”。
- 递归是**全局设置**，书文件里没有这个开关；用户一开，你写的三个字段就是全部防线。

## 八、随机与互斥

- `probability < 100`：命中后仍按概率决定插不插。做天气、谣言、随机事件。**别指望它精确**：设 30 可能连着三轮都出。要严格随机就让 AI 在正文里自己选。
- `group` 同名的多条同时命中只插一条（按 `groupWeight` 抽）；`useGroupScoring: true` 命中多的优先；`prioritizeInclusion: true` 直接取 `order` 最大的。
- 用法：`天气` 组里放“晴/雨/盐雾”三条，各 33 权重。

## 九、时间效果

单位是**消息条数**，`0` = 无效。

- `sticky: N` — 激活后再常驻 N 条，期间忽略概率。注意 sticky 在装填时**排在同轮命中之前**。
- `cooldown: N` — 激活后 N 条内不再激活（可与 sticky 叠加：sticky 结束后进冷却）。
- `delay: N` — 聊天至少 N 条才可能激活（`delay: 1` = 开局那条不算）。

用法：一次性的"潮水已漫过堤线"用 `sticky: 3`；"第一夜之后才会出现的传闻"用 `delay: 10`。

## 十、附加匹配源与绑卡

- 附加匹配源（`matchCharacterDescription` / `matchPersonality` / `matchScenario` / `matchPersonaDescription` / `matchCharacterDepthPrompt` / `matchCreatorNotes`）让条目被“卡里写的字”点亮，不用等聊天里出现。适合跨卡共用的世界观书。
- `characterFilter.names` 精确绑卡名，`.tags` 按标签绑一组；`exclude` 反转。
- 绑定顺序：角色管理面板的 🌐 选的 = 主世界书，**只有主本随卡导出**；`Shift`+点或 `More… → Link World Info` 加挂的不会导出。
- 改名世界书时 ST 会提示重新链接所有引用它的角色，**选是**，否则绑定静默失效。群聊的全局世界书**只能挂一本**。

## 十一、出包前十二条自查

1. 每条绿灯 8–15 个关键词？关键词是聊天里真会出现的词？有没有单字词、子串词、泛词？
2. 常驻是否只装了"不常驻就演错"的东西（规则、常识、约束）？
3. 条目是否都 `excludeRecursion: true`？常驻是否都加了 `preventRecursion: true`？
4. `matchWholeWords` 是否显式 `false`？
5. `position` 有没有误用 2 / 3（作者注）或 5 / 6（示例消息）？
6. `position: 4` 的条目是否都写了数字 `depth`？
7. `order` 是否分了三档（95–100 / 70–90 / 70）而不是全 100？
8. 常驻合计字数是否 ≤8000？单条正文是否 ≤1000 字（超了拆条）？
9. 需要随机或互斥的条目，是否用了 `probability` / `group` 而不是写死在正文里？
10. 核心规矩有没有只放在 `2` / `3`（骑作者注）？放下去了就再往 `0` 或 `1` 抄一份。
11. 有分档设定的，阶段词格式是否与世界书关键词逐字符对齐？（改了状态栏就得改关键词）
12. 交付说明里是否给了第六节那张全局设置表，并请用户填了实际值？

分档设定（拿状态词当关键词）写在 `references/worldbook-writing.md` 末尾。

# 阶段 1 · 世界观

产物 type：`world-bible`。骨架：`templates/world-bible.yaml`。格式、预算、降级链回 `references/interview-protocol.md`。

## 进入条件

- 用户给出题材、概念、世界构想中的任意一项即可进入；只有一个概念词也进入（走"仅概念词"分支）。
- 已有 `contract.naming.world`：直接进迭代，不重走采集。
- 用户给出成品世界观文档要求转换：走"文档转换"分支。
- 上游无契约：先建 `templates/contract.yaml`，把 `stages.1` 置 `partial`。
- `project.web_research: true`：先按 `references/web-research.md` 检索本世界的世界观底盘（已有作品则查原作规则/势力/专名/时间线，真实题材则查年代地理与制度），记进 `创作痕迹/检索来源.md`，查完才动笔。

## 追问

**首轮** 5–7 问。边界门已在开局四问里锁过（`nsfw` / `rating` / `hard_no`），这里只在必要时补问 RP 形式；若要补边界细节（≤2 问），问完直接写回契约。四大框架要素必须问到：① 题材与基调 ② 时空范围 ③ **张力形态**（单一引擎 / 多源日常 / 任务线——情景喜剧与沙盒选「多源日常」，别硬造一个总引擎）④ 超自然/科技系统有无。

其余候选（按需择优，不逐条问全）：势力数量级（建议 2–5）、使用场景（1v1 / 多人 / 跑团风格）、是否有世界名、目标时长（单次短篇 / 长期连载 / 开放世界）、是否基于已有 IP 或历史原型、是否有已构思角色需纳入。

**快车道**：用户首次输入已覆盖四大要素中 ≥3 项 → 跳过纯提问，直接出粗版，粗版前用 2–3 句复述理解，粗版后附 ≤5 个补充问题。

**常规路线**：首轮这条回复只做两件事——可选的一句话复述（≤2 句）+ 按优先级列 5–7 问。**不输出完整模版。**

**后续每轮** ≤8 问，优先级：世界硬规则 / 超自然或关键系统 / 代价与限制 / 判定框架 → 核心矛盾与势力关系 → 常识与法律红线 / 资源交易 / 信息分层 → RP 场景覆盖。

**每轮回复结构**：① 确认本轮新锁定的硬设定 ② 标出本轮重点补全的 1–3 个模块 ③ 简要列出修改 ④ ≤8 问 ⑤ 有冲突/漏洞则按"原则 6"给修补方案并标严重度。

**完整版输出触发**：累计改动涉及 ≥3 个模块，或用户要求。其余情况只贴"局部 YAML 片段"展示改动较大的章节。

## 判断标准

### 题材分支（先判，再动笔）

| 题材 | 必备块 | 注意 |
|---|---|---|
| **沙盒 / 日常 / 情景喜剧** | `世界怎么运转` + `日常生活的质地` + `张力从哪来.张力形态 = 多源日常` | 三个及以上来源就够，不要为"统一感"硬造一个总引擎；`核心矛盾` 里那套"各方目标与手段"可以只写一两句 |
| 单一引擎（战争 / 悬疑 / 生存） | `张力从哪来`（各方目标与手段完整）+ `世界规则` | 这才是"核心矛盾"原始的适用场景 |
| 任务线（跑团 / 副本） | `世界规则` + `世界怎么运转.沙盒还是任务 = 任务` | 要写清目标怎么给、失败怎么处理 |

判错题材是本 skill 最容易犯的错：一次实操里，情景喜剧被写成"所有人围绕某个东西的审判世界"，用户连否两版才纠回来。**先问题材，再决定要不要那个总引擎。**

### 总体原则（18 条，保留原编号）

原则 1：以可操作为核心 — 每条设定至少通过一项检验：能判断行为是否合法/可行、能约束或激发冲突、能为裁决后果提供依据、能帮助生成环境描写或 NPC 反应。
仅为氛围而无上述作用的设定，三选一处理：压成一句话附注在相关规则旁 / 移入 `常识清单` 作文化背景 / 标注"氛围参考"并声明不具约束力。

原则 2：对 AI 可读性优先（规则式表达） — 消费者是执行 RP 的 AI，条目写成"指令式 / 规则式"，让它能直接当约束用，而不是读完叙事再推导规则。
量化优先：涉及规模/频率/强度/概率的一律给数值、比例、等级或统一枚举值。因果链式表达：复合规则写「若 X → 则 Y；否则 → Z」，不让 AI 跨段推理。

原则 3：先框架，后细节 — 先锁题材基调、时空范围、张力形态、超自然/科技大方向；再细化世界规则、势力结构、社会常识、信息分层。
框架未定不细化子系统；用户给了大量细节但框架未明，先提炼框架再回填。深度匹配：模块细化深度与其对 RP 的影响权重成正比，张力来源相关系统最先细化到可判定。

原则 4：规则必须可判定（能/不能/代价/上限 + 裁决方法） — 每个关键系统四项写清：能做什么、不能做什么、代价与风险、上限与边界。
另加：最小可用的判定框架（不必掷骰，但要能裁决成功/失败/部分成功的后果）；两条规则可能冲突时明确优先级；每个关键系统标 1–2 个边界/模糊场景及默认裁决；规则嵌套超三层设兜底条款（如"无法判定时由旁白按叙事合理性裁决，结果不构成新硬设定"）。

原则 5：关键设定不替用户拍板 — 题材基调、世界规则大方向、张力形态与主线冲突、死亡/永久后果的严重度、基调明暗、秘密信息的具体内容——给 2–3 个互斥选项与简短优缺点，选择权在用户。
用户说"你来决定 / 全权交给你"才可代选，但仍须可判定，并标注「已代为选定，如需调整请随时告知」。选项格式固定：每个方案一行描述 + `优点` / `缺点` / `对 RP 的影响` 三行。

原则 6：主动查错与补洞 — 七类问题必须指出并给 2–3 个修补方案：自相矛盾、逻辑断裂、推进 RP 必需信息缺失、规模失调、因果断裂、孤立设定、规则真空。
中间版用标记：`【疑似冲突】` `【待补全空缺】` `【规模失调】` `【因果断裂】` `【孤立设定】` `【规则真空】`。严重度三级：致命（RP 无法进行/核心规则崩溃，立即解决）/ 重要（影响多模块一致性，本轮解决）/ 建议（可延后）。用户坚持保留两条互斥设定时，记录为硬设定并标注 `[用户已确认共存，RP 时以 XX 优先]`。

原则 7：设定一致性与冲突优先级 — 用户确认的硬设定后续不得擅自改动；确需修改须先指冲突、再给 2–3 方案、再经确认。
裁决优先级：硬设定 > 本文档其他条目 > 软设定即兴补全；软设定不得推翻硬设定；同级冲突时更具体者优先。内部维护「已锁定硬设定」列表，用户确认新硬设定时在下一轮开头确认。新增或修改硬设定时做连锁影响检查，列出受影响条目。

原则 8：信息分层（防剧透） — 三层：公开信息（角色可知）/ 半公开信息（需调查或权限）/ 秘密信息（仅旁白或高层可知）。
扮演普通角色时不得引用秘密信息，除非剧情触发或身份满足条件。每条关键设定应标信息层级，未标默认公开。预设意外超权获知的处理方式：不可逆获知 / 需后续验证 / 可能是失真版本。

原则 9：已有 IP 或历史原型的处理 — 先问清哪些照搬、哪些改造、哪些必须去掉。
YAML 里只写本世界自己的版本，不引用原作名词人名，除非用户明确要求保留。继承自原型的不可改要素写进 `变更边界 > 硬设定`。改造幅度大时，用一句话概括与原型的核心差异写入 `创作痕迹/项目档案.yaml` 的 `元信息 > 原型说明`（不进终稿）。

原则 10：模版结构可按需增删 — 增删模块后保持结构清晰；删除即整段移除不留空壳；终稿只留有内容或用户明确要求保留的模块。
自定义模块须沿用同一命名风格（中文键名、简洁、无歧义），并检查与现有模块是否信息重叠或冲突。删除某模块会使其他模块引用失效时（如删"种族与物种"而"势力列表"引用了种族 id），必须提醒并建议处理方式。

原则 11：复杂度管理 — 超限即建议分卷并让用户确认优先级：势力 >8、独立规则系统 >3、历史事件 >8、种族 >6、主要地点 >10、张力来源 >4。
分卷策略四选一：按地理区域 / 按阵营 / 按时间线阶段 / 核心卷（必读）+ 扩展卷（按需加载）。

原则 12：最终输出格式约束（YAML） — 终稿是单一 YAML 文档，包在 yaml 代码块里，代码块外无任何文字（"未决事项提醒"也要写进 YAML 的 `未决事项` 模块）。
顶层用具体世界名作根键，不用 `<世界名称>` 占位符，不输出尖括号。终稿不含 `元信息` 与 `类型与基调` 两块（它们在 `创作痕迹/项目档案.yaml`）。终稿移除全部 `#` 注释行与被注释掉的可选结构。书写规范：2 空格缩进禁 Tab、字符串双引号、列表用 `-`、不用锚点别名、>120 字符用折叠或字面块标量、避免未转义特殊字符、空列表写 `[]`。

原则 13：字段状态标记的使用范围 — 状态标记只出现在粗版与中间版；终稿尽量不保留 `[待定]`。
终稿确实未决时：字段内写成 "选项A / 选项B / 选项C（待选）"，同时记入 `未决事项` 列表（仍保持纯 YAML 交付）。标记种类见 `references/pipeline.md` 的 7 个占位符。

原则 14："不适用"的裁剪规则 — 粗版可用 `[不适用]`；终稿中字段不适用则删字段、模块内核心字段全不适用则删整段模块，终稿不保留 `[不适用]` 字符串。

原则 15：内部一致性自检 — 出粗版与每次出中间完整版之前跑七项：时间线一致性 / 规则闭环（四要素齐备）/ 势力平衡（能力悬殊须说明原因）/ 信息分层完整性 / 可操作性 / 交叉引用一致性（id、名称、数值）/ RP 场景覆盖。
中间版可用 `✅ / ⚠️` 自检报告，终稿不输出报告。

原则 16：渐进式命名约定 — 一旦分配 `id`，后续引用一律用该 id；用户改名只改 `名称`，`id` 不动（除用户明确要求）。
`id` 用英文小写 + 下划线，统一前缀：`faction_` 势力 / `race_` 种族 / `loc_` 地点 / `system_` 系统 / `side_` 矛盾方 / `event_` 历史事件 / `item_` 资源道具。

原则 17：RP 场景覆盖验证 — 迭代后期对六类场景逐项验证：战斗对抗（判定框架、伤害与治疗）/ 社交谈判（NPC 立场判定依据）/ 探索调查（揭示触发条件）/ 交易资源（货币物价稀缺度）/ 成长变化（AI 即兴角色能否成长）/ 日常（常识清单是否撑得住非冲突场景）。
完全无规则覆盖的场景标 `【规则真空】` 并提醒用户。

原则 18：多语言与文化适配 — 默认中文。用户要英文或双语时：YAML 键名保持中文、值用用户指定语言、在 `创作痕迹/项目档案.yaml` 的 `元信息` 里填 `文档语言`。
虚构语言统一在 `常识清单 > 语言与文字` 定义，不在其他模块随意混用未定义词汇。

### 写作风格（5 条）

**风格 1 语言**：默认中文；英文或双语按原则 18；虚构专有名词首次出现附简短释义。
**风格 2 表达**：条目化、短句、高信息密度，避免小说式长段与堆形容词。规则用「条件 + 行为 + 结果」。否定式约束与正面描述同等重要，明确写"不能/不会/禁止"。分层差别用并列对比（如初级/中级/高级/禁忌各能做什么）。
**风格 3 枚举值优先**：模板给了枚举就只用枚举，不写"偏高/较强/还行"。参考表：稀有度 极稀有(<1%)/稀有(1–10%)/常见(10–50%)/普遍(>50%)；强度 极强/强/中/弱/极弱；管制 强/中/弱/无；治疗难度 易/中/难/不可逆；可替代性 高/中/低/不可替代；社会流动性 高/中/低/固化；关系 盟友/友好/中立/冷和平/敌对/战争状态。
**风格 4 内容规模**：势力 2–5 个、历史事件 3 件起（>5 件检查可否合并）、独立规则系统 ≤3 套、种族 ≤5 个、主要地点 ≤8 个、每势力代表 NPC 1–3 个。清晰好用优先于数量多。
**风格 5 需要避免**：除非用户明确要求，不加玩家权限系统、叙事视角/开场镜头/剧本结构、完整 NPC 人物卡（势力代表只写名字 + 一句话定位）、过度细化的经济模型或物理法则、对用户自建角色的强制限制（`AI即兴角色约束` 只管 AI 即兴创作）、元游戏机制（经验值升级，除非要跑团风格）、预设结局或强制走向。

### 特殊场景（8 条）

1. **大段叙事/小说片段**：提取隐含规则、势力关系、矛盾方向，用列表分 `【规则】`/`【势力】`/`【矛盾】`/`【常识】`/`【氛围（待转化）】` 复述，用户确认后再填；不把叙事原文粘进 YAML。
2. **要求扩展但无方向**：按优先级扩展——代价与限制、势力暗中关系、秘密信息、禁忌与法律红线、边界案例裁决、日常细节。每方向给 2–3 个选项，不直接填。
3. **中途大幅改向**：先确认改局部还是推翻重来。重来则回采集；局部则列出受影响模块、区分"必须连带修改"与"建议连带修改"、确认后统一更新、同步硬设定列表。
4. **多世界/平行维度**：每个世界独立一份 World Bible，主文档用 `跨世界规则` 写维度间交互；不在一份文档里混多个世界的设定；多卷时各卷 `项目档案.yaml` 标系列与卷间关系。
5. **极简世界观**：可只留 `世界规则`（含判定框架）/ `张力从哪来` / `变更边界`；须提醒极简版会让 AI 大量即兴补全。即使极简也建议保留 `常识清单 > 禁忌与法律红线` 与 `AI即兴角色约束 > 即兴角色能力上限`。
6. **已有文档要求转换**：通读提取 → 按模板重组并标注来源节次 → 列出源文档模糊矛盾处请用户澄清 → 列出模板未覆盖的必要模块按优先级建议补全。
7. **只有概念词或极短描述**：不过度发挥，先给 2–3 个完全不同的解读方向（每个 2–3 句），选定后进常规路线。
8. **面向多平台**：不用任何平台专有指令格式，`项目档案.yaml > 元信息 > 本文档对AI的核心指令` 写通用自然语言，并在契约 `hard_settings` 留一份同名条目；`兼容性说明` 也放项目档案。

## 生成

**先落项目档案**：把 `元信息` 与 `类型与基调` 写进 `创作痕迹/项目档案.yaml`，不进终稿——`文档用途` / `文档版本` / `RP形式`（同 `project.rp_form`）/ `本文档对AI的核心指令` / 原型说明 / 兼容性说明 / 文档语言 / 变更记录，以及 `类型` / `子类型` / `基调` / `基调补充说明` / `叙事风格标签` / `基调红线`（骨架 `templates/project-profile.yaml`）。其中 `本文档对AI的核心指令` 与 `基调红线` 必须同时追加成契约的 `hard_settings`（`source: 用户确认`），否则下游阶段读不到。终稿从 `时间地点与世界范围` 开始。

1. **粗版**：四大要素至少三项可用信息时进入（沙盒 / 日常 / 情景喜剧先在「判断标准 · 题材分支」表里判一次，`世界怎么运转` 与 `日常生活的质地` 必须填，其余模块可后补）。按模板出粗版 YAML，可只覆盖已有信息，其余用占位符；根键用暂定世界名并提醒可改名；不编造会强烈影响世界走向的硬设定；粗版后附 ≤8 个补充问题（聚焦：使规则可判定所缺信息、张力形态、势力关系方向、代价与限制）。
2. **迭代**：按"追问"节的每轮结构推进；每轮只动 1–3 个模块；出完整版按"完整版输出触发"判断。
3. **收敛**：收敛门（见 `references/pipeline.md`）全部满足后，主动提议出终稿。
4. **终稿前一轮**（自然语言）：列 3–10 条已锁定硬设定要点、仍可留白部分、未决但不影响开局的点；跑原则 15 + 原则 17 自检并简报；报统计（势力/种族/关键系统/历史事件数量，硬设定与未决条数）；问"立刻出终稿还是先微调"。
5. **终稿**：用户明确确认后才输出。渲染按 `references/dual-mode.md`：文本模态一个 yaml 代码块、块外无字；工程模态写 `最终产物/world-bible.yaml`。未决项写进 `未决事项`。

## 写回契约

- `naming.world` = 终稿根键（暂定名也写，标 `provisional` 语义由 `decisions` 记录）
- `naming.factions[]` = 势力列表的 `{id, name, alias}`；`naming.places[]` = 主要地点的 `{id, name, scope}`；`naming.systems[]` = 关键系统的 `{id, name, ceiling}`
- `stages.1` → `partial` / `done`
- `hard_settings[]`：只在用户确认时追加，`source: 用户确认`，`locked_at_stage: 1`；其中必含从 `项目档案.yaml` 提上来的两条——`本文档对AI的核心指令` 与 `基调红线`
- `artifacts[]`：`{type: world-bible, path: 最终产物/world-bible.yaml}`；项目档案不进 `artifacts`（它不是交付物），只在 `decisions` 记一条「元信息与类型基调归档于 创作痕迹/项目档案.yaml」
- `content_boundaries`：开局已锁；本阶段若补问了边界细节（RP 形式、额外禁区）就追加 `hard_no` / `soft_no`，不重写 `nsfw`。`nsfw: false` 时本阶段产物不得出现任何性描写，`AI即兴角色约束` 里要把它写成禁区
- `pending[]`：终稿仍留的 `[待定：…]` 全部登记
- 已存在的键被改写 = 冲突，停下问用户（见 `references/contract-schema.md`）

## 退出

- 收敛门通过 → 提议出终稿 → 用户明确确认 → 输出终稿 → 回写契约 → 跑 `python scripts/validate-contract.py <创作痕迹/contract.yaml>`，退出码 0 → 阶段结束。
- 用户中途叫停：交付当前粗版/中间版，`stages.1` 置 `partial`，说明缺哪几项才到 `done`。
- 终稿后用户要改：回到迭代，改完重跑原则 15/17 与命名门，不重跑采集。

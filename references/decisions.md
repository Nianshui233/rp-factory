# 决定、缺口与「未答」

这一页解决一个反复出现的失效：**把「用户没回答」当成「用户同意」**。一旦发生，后续每一阶段都在替用户重做同一个决定，而用户第一次看到成品时才发现方向不对——那时改的代价最大。

所以每个决定必须带两个东西：**状态**（谁签的字）和**缺口级别**（不改会怎样）。

---

## 一、四态

写进 `contract.decisions[]` 的 `state` 字段（`scripts/validate-contract.py` 的 C13 会查）。

| state | 含义 | 谁签的字 | 后续动作 |
|---|---|---|---|
| `confirmed` | 用户明确说了要这个 | 用户 | 不许再改；要改必须重新问，并把旧记录标 `rejected` 另起一条 |
| `proposed` | **我替用户定的**，已告知，可被推翻 | 助手 | 必须写 `why`；交付说明里点名；用户否掉就改 `rejected` 并重问 |
| `pending` | 问了，用户没答 / 答不了 | 无 | 同时进 `contract.pending[]`（阶段 + 缺什么）；下游只许用最小默认值并标 `[待定：…]` |
| `rejected` | 用户否定过 | 用户 | 永不复活；想再提必须用户自己先开口 |

三条硬规矩：

1. **`proposed` 必须带 `why`**。没有 `why` 的 proposed 和 confirmed 在纸面上没区别，C13 直接判失败。
2. **`answer` 里写着「没回答」就不许是 `confirmed`**。C13 会查关键词（没回答 / 未答 / 未确认 / 用户未定），这是伪造签字。
3. **`pending` 与 `contract.pending[]` 同时存在**。`state: pending` 是「这个决定悬着」，`pending[]` 的一条是「这一阶段缺什么、缺了会怎样」——两者都要写，脚本各查一半。

## 二、缺口分级

阶段收尾（自检门之后、跑 `check-stage.py` 之前）给每个未解决项定级，写进交付说明与 `pending[]` 的 `item` 描述里。

| 级别 | 判据 | 处理 |
|---|---|---|
| **致命** | 缺了它，下游阶段无法开工；或交付后用户必然要重做这一块（例：世界怎么运转空着就做角色，角色的动机无从推） | 停下问，不带着它推进 |
| **重要** | 能推进，但会在成品上留下明显空洞（例：关键 NPC 的阵营没定） | 用默认值推进，标 `proposed` 并在交付说明点名 |
| **次要** | 只影响风味（例：某个次要地点的季节） | 直接给默认值，不占提问预算，不点名 |

提问预算按 `references/interview-protocol.md`：补采访问 ≤3 问，只问致命；重要级走「默认 + 点名」；次要级不问。

## 三、未答不是委托

用户沉默有三种，处理完全不同：

- **没看到**（问题藏在长回复里）→ 换位置再问一次，一句话问清。
- **不想定**（「你看着办」）→ 这就是委托：给默认值，记 `confirmed` 并在 `choice` 里引用用户原话（「你看着办」本身也是签字）。
- **答不了**（超出用户知识面的技术选择，如 `position` 枚举该填几）→ 不给用户做选择题：直接按最优解做，记 `proposed` + `why`，在交付说明里用一句话解释，不问。

反例（真实踩过）：开局问「要不要 NSFW」，用户回「随便」→ 记 `pending` 然后整包按 SFW 做，交付时用户说「我以为是成人向」。正确做法是把「随便」当委托：按 `nsfw: false` 落，记 `confirmed`，`choice` 写「用户答『随便』，按否锁」，并在交付说明第一句说明。

## 四、记录的样子

```yaml
decisions:
  - item: 数值上限
    choice: 好感 0–100 / 体力 0–10 / 理智 0–100
    state: proposed
    why: 用户没有偏好，按「读数稳定 + 变化可感知」取的常见档位
  - stage: world
    question: 世界怎么运转
    answer: 灵气浓度决定寿命
    state: confirmed
  - item: 反派动机
    choice: 未定（用户说回头再想）
    state: pending

pending:
  - stage: cast
    item: 反派动机——不定它，两个配角的忠诚线无法收口（重要级）
```

`item` + `choice` 是过程决策，`stage` + `question` + `answer` 是阶段决策；两种都收（C12）。`state` 两种都能挂（C13）。

## 五、什么时候必须写

1. 开局四问答完（`project.stages_requested` / `web_research` / `content_boundaries`）。
2. 每个阶段首轮：本阶段替用户拍了什么。
3. 用户否掉任何东西——立刻记 `rejected`，不要留着旧记录等它「复活」。
4. 阶段收尾：本轮落下什么 / 哪些是我替你定的 / 哪些还悬着 / 下一步是哪一阶段。
5. 中途改契约（改名、开关边界、改阶段清单）——见 `references/contract-schema.md` 的「中途改动」表。

交付说明固定四句，就按第 4 条那个顺序写；不要用「已完成」替代「哪些是替你定的」。
